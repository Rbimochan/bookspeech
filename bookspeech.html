BookSpeech

EPUB → audiobook (.m4b) converter. Local-first TTS via Kokoro-82M (swappable engine interface for XTTS-v2 later), FastAPI backend with job queue, simple local web UI. This document is the full build plan: 10 plans × 10 sub-plans = 100 actionable tasks, in build order. Hand this whole file to Claude Code as the spec.

10 plans
100 sub-plans
Kokoro-82M default TTS

PLAN 1

Project Setup & Environment

Get a clean, reproducible dev environment before any feature code.
  1. Create repo structure: backend/, frontend/, storage/uploads, storage/output, tests/
  2. Init Python project with uv or poetry; pin Python 3.11+
  3. Add core deps: fastapi, uvicorn, ebooklib, beautifulsoup4, ffmpeg-python, mutagen, pydantic
  4. Add TTS deps: kokoro-onnx (or kokoro pip pkg) + onnxruntime (GPU variant if CUDA available)
  5. Verify ffmpeg binary is installed on system PATH; document install steps per OS
  6. Set up SQLite file for job/book metadata (no external DB dependency for v1)
  7. Create .env.example for config: storage paths, max concurrent jobs, default voice
  8. Add Makefile or simple scripts: run-backend, run-frontend, run-tests
  9. Set up basic logging config (structured, per-job log file under storage/logs/<job_id>.log)
  10. Write root README.md with architecture diagram and setup instructions
PLAN 2

EPUB Parsing

Reliably extract clean, ordered chapter text and metadata from arbitrary epub files.
  1. Build epub_parser.py using ebooklib to load an epub file
  2. Extract book-level metadata: title, author, cover image, language
  3. Walk the spine in reading order (not just file order) to get correct chapter sequence
  4. For each spine item, extract raw XHTML and parse with BeautifulSoup
  5. Detect chapter boundaries: use <h1>/<h2> headings or spine-item splits as chapter markers
  6. Extract plain text per chapter, preserving paragraph breaks
  7. Handle nested/multi-file chapters (some epubs split one chapter across multiple XHTML files)
  8. Extract cover image separately for embedding into final .m4b metadata
  9. Build a Book data model: {title, author, cover_path, chapters: [{index, title, text}]}
  10. Write parser tests against 3–5 real-world epub samples (Project Gutenberg is a good free source) covering different structures
PLAN 3

Text Cleaning & Normalization

Turn raw extracted text into TTS-ready text. This is the highest-leverage module for output quality.
  1. Strip residual HTML tags, entities, and non-content artifacts (page numbers, running headers)
  2. Remove or resolve footnote/endnote markers (e.g. superscript numbers) — either drop or inline as parenthetical
  3. Normalize whitespace: collapse multiple newlines/spaces, fix hyphenated line-break words ("exam-\nple" → "example")
  4. Number normalization: dates, currency, ordinals, decimals → spoken form (use a lib like num2words or write targeted rules)
  5. Abbreviation expansion: "Dr.", "Mr.", "e.g.", "etc." → spoken form, with a configurable dictionary
  6. Handle quotation marks and em-dashes so TTS pacing doesn't stumble (normalize curly quotes, spacing around dashes)
  7. Detect and flag non-English/foreign phrases (option to skip TTS-mangling or mark for manual review)
  8. Strip or convert tables/lists to something speakable (or flag as "skipped — not suitable for audio" in the job log)
  9. Build a pluggable rules pipeline (ordered list of normalization functions) so rules can be added without touching core logic
  10. Write unit tests with tricky real sentences (numbers, abbreviations, nested quotes) asserting exact normalized output
PLAN 4

Chunking Engine

Split cleaned chapter text into TTS-safe chunks without breaking prosody at bad points.
  1. Determine Kokoro's practical max input length per call (empirically test, then set safe ceiling)
  2. Implement sentence segmentation (use nltk/spacy sentence tokenizer, not naive regex split on periods)
  3. Group consecutive sentences into chunks up to the char/token ceiling, never splitting mid-sentence
  4. Prefer paragraph boundaries as chunk boundaries when they fit within the ceiling (better prosody continuity)
  5. Handle edge case: single sentence longer than max chunk size (split on clause/comma as fallback)
  6. Preserve chunk-to-source mapping (chunk index → original paragraph/sentence range) for debugging
  7. Attach chapter/chunk sequence numbers so audio assembly can reorder reliably even with async/parallel synthesis
  8. Add a dry-run mode: output chunk boundaries as text/JSON without running TTS, for QA before burning compute
  9. Make chunk size configurable per TTS engine (Kokoro vs XTTS will have different limits)
  10. Write tests: verify no chunk exceeds limit, no sentence is split, and chunks reassemble to original text losslessly
PLAN 5

TTS Engine Integration (Kokoro)

A clean, swappable TTS engine interface with Kokoro as the default implementation.
  1. Define abstract TTSEngine interface: synthesize(text: str, voice: str, speed: float) -> np.ndarray/wav bytes
  2. Define list_voices() -> List[VoiceInfo] method for UI voice selection
  3. Implement KokoroEngine using kokoro-onnx, loading the ONNX model once at startup (not per-request)
  4. Handle sample rate consistency (Kokoro outputs at a fixed rate — document and enforce it downstream)
  5. Add GPU/CPU auto-detection for onnxruntime provider selection
  6. Implement batching if Kokoro supports it, to speed up multi-chunk synthesis
  7. Add per-chunk retry logic (TTS calls can occasionally fail/produce garbage — detect near-silent/empty output and retry)
  8. Save each synthesized chunk as a temp wav file under storage/uploads/<job_id>/chunks/
  9. Stub out XTTSEngine class (not implemented yet) so the interface is proven pluggable from day one
  10. Write a standalone script/test that synthesizes one paragraph end-to-end and plays/saves it, for fast manual QA
PLAN 6

Audio Assembly & M4B Packaging

Turn synthesized chunk audio into one properly chaptered, metadata-rich .m4b file.
  1. Concatenate chunk wavs into one wav per chapter, in correct order, with small configurable silence gaps between sentences/paragraphs
  2. Track chapter start/end timestamps in seconds as chapters are concatenated
  3. Concatenate all chapter wavs into one full-book wav (or stream via ffmpeg concat demuxer to avoid huge memory use)
  4. Encode final audio to AAC via ffmpeg (.m4b container = m4a/AAC with audiobook flag)
  5. Generate ffmpeg chapter metadata file (;FFMETADATA1 format) from tracked chapter timestamps
  6. Embed book metadata into the .m4b: title, author, cover image (from Plan 2), narrator = "BookSpeech / Kokoro"
  7. Set correct audiobook-specific tags so apps like BookPlayer/Apple Books recognize it as an audiobook (genre tag, media type)
  8. Clean up intermediate chunk/chapter wav files after successful final assembly (configurable: keep for debug vs delete)
  9. Verify output: parse the generated .m4b back out (via mutagen) and assert chapters/metadata are present and correct
  10. Handle large-book memory/disk safety: stream-based ffmpeg concat rather than loading full book into memory
PLAN 7

Job Queue & Backend API

Non-blocking job orchestration so multi-hour conversions don't hang HTTP requests, plus a clean API for the UI.
  1. Design Job model: id, book_title, status (queued/parsing/cleaning/synthesizing/assembling/done/failed), progress_pct, current_chapter, error_msg, output_path
  2. Implement lightweight background worker (asyncio task queue for v1; note upgrade path to rq/celery if scaling needed)
  3. Enforce max concurrent jobs (configurable, default 1–2 given TTS is compute-heavy) with a queue for the rest
  4. POST /books/upload — accept epub file, parse metadata immediately, return book preview (title, author, chapter count, cover) without starting synthesis
  5. POST /jobs — start a conversion job given book_id + voice + speed, returns job_id
  6. GET /jobs/{id} — poll job status/progress
  7. GET /jobs/{id}/stream — optional SSE endpoint for live progress push instead of polling
  8. GET /jobs/{id}/download — stream the finished .m4b file
  9. GET /voices — list available TTS voices (delegates to TTSEngine.list_voices())
  10. Persist jobs/books to SQLite so history survives a backend restart; add GET /library listing past conversions
PLAN 8

Frontend Web UI

Simple local web UI: upload, configure, watch progress, download — nothing fancier than needed.
  1. Choose stack: plain HTML + HTMX/Alpine, or minimal React+Vite (pick one — don't over-engineer for a local tool)
  2. Build UploadView: drag-and-drop epub upload, show extracted title/author/cover/chapter count on success
  3. Build voice selection control, populated from GET /voices, with a "preview" button (see Plan 9)
  4. Add speed/speaking-rate slider if Kokoro supports rate control
  5. Build "Start conversion" action → calls POST /jobs, transitions to progress view
  6. Build ProgressView: overall % bar + current chapter name/index, polling or SSE-driven
  7. Handle failure state in UI: show error message and a retry action if a job fails
  8. Build LibraryView: list past books/jobs with status, download link for completed ones
  9. Add basic responsive layout (desktop-first is fine, it's a local tool) and dark theme consistent with a "book/audio" aesthetic
  10. Wire up download button to GET /jobs/{id}/download, triggering browser file save
PLAN 9

Voice Preview & Selection

Let the user hear a voice before committing to a multi-hour job.
  1. Curate a short fixed preview sentence (~10–15 words) used for all voice previews
  2. Add POST /voices/{voice_id}/preview — synthesizes the preview sentence on demand, returns audio
  3. Cache preview audio per voice on first generation (avoid re-synthesizing the same preview repeatedly)
  4. Add inline audio player per voice option in the UI dropdown/list
  5. Show voice metadata if available (gender, accent/language, sample rate) alongside preview
  6. Allow the user to type a custom preview line (optional, uses their own book's opening line for a truer preview)
  7. Handle preview failure gracefully (voice unavailable/model error) without blocking the rest of the UI
  8. Persist the user's last-selected voice as a UI default for next session (localStorage or simple cookie)
  9. Add speed preview too — regenerate preview when speed slider changes
  10. Write a quick manual QA checklist: preview every bundled Kokoro voice once, note any that sound broken
PLAN 10

Testing, Error Handling & Deployment

Make it robust enough to trust with a real multi-hour book conversion, and easy to run locally.
  1. Define failure modes explicitly: corrupt epub, unsupported DRM'd epub, TTS engine crash mid-book, disk full, ffmpeg missing
  2. Add input validation on upload (file type, size limit, reject DRM-protected epub with a clear message)
  3. Add resumable jobs: if synthesis fails at chapter N, allow resuming from N rather than restarting the whole book
  4. Add end-to-end integration test: real small epub (public domain, 3–4 short chapters) → full pipeline → verify valid playable .m4b with correct chapter count
  5. Add performance benchmark script: measure synthesis time per 1000 words on target hardware, surface expected total time estimate to user before starting a job
  6. Add disk space check before starting a job (estimate output size, warn if insufficient)
  7. Write a single docker-compose.yml (or documented native setup) bundling backend + ffmpeg + model weights for easy local spin-up
  8. Add a settings page/config file for defaults: default voice, max concurrent jobs, output directory location
  9. Write troubleshooting doc: common ffmpeg errors, ONNX runtime GPU setup issues, epub parsing edge cases
  10. Final smoke test: convert one full-length real novel start to finish, listen to first/last chapter and one random middle chapter for quality check
BookSpeech build plan — 10 plans × 10 sub-plans = 100 tasks. Recommended build order: 1 → 2 → 3 → 4 → 5 → 6 (prove the core pipeline end-to-end as a script) → 7 → 8 → 9 → 10.
